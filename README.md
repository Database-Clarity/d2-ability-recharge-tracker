# Destiny 2 Ability Recharge Tracker

A Windows overlay for timing grenade, melee, and class-ability recharge from the visible Destiny 2 HUD. It samples screen pixels only and does not read game memory. Global low-level keyboard and mouse hooks support configurable input bindings; they pass all input through to other applications. Gameplay input is sent only while an explicitly started repeatability test is active and only when Destiny 2 is the foreground application.

## Run

1. Download `D2AbilityTracker-v<version>-Setup.exe` from the [latest release](https://github.com/Database-Clarity/d2-ability-recharge-tracker/releases/latest).
2. Run setup on Windows x64. If the .NET 9 Desktop Runtime is missing, setup asks permission, downloads its installer directly from Microsoft, verifies its digest, and installs it automatically. An internet connection is required only for a missing runtime; future app updates reuse the shared installation instead of downloading .NET again. Setup requires administrator approval and creates a Start menu shortcut. These builds are unsigned, so Windows may show an unknown-publisher warning.
3. Keep Destiny 2 visible and select an ability slot. The selector finds the Destiny 2 window and opens a frozen preview of it; if the game is not found, it offers the selected display preview as a fallback. Select the full square slot tightly, including its border. A small strip below the selection is captured automatically. Repeat for grenade, melee, and class ability as desired.
4. Leave detection on with the ability charged initially so its ready color can be learned. The timer starts on the ability-use flash. The completion flash or first returning ready fill is confirmed by stable ready color, while its first timestamp is retained as the endpoint. The measured duration remains visible after completion, in total seconds to two decimal places alongside minutes/seconds (for example, `73.46 s (01:13.46)`). Repeat-test averages use the same format.

The overlay is included in desktop/display screen capture. Game-only capture records Destiny 2's own render surface and may not include this separate overlay window; use display capture to record both.

The selector shows a frozen preview of the Destiny 2 window when it is detected, or the chosen display as a fallback. Zoom with the mouse wheel or +/- and pan with right- or middle-drag. Drag a selection to move it, or drag a corner to resize it; the selection is only saved after choosing **Use selection**, either beside the active selection or in the footer. The illustrated guide compares whole-slot and icon-only selections and shows the bottom-border start flash. Regions are saved relative to their display and scaled when its resolution changes (for example, setup at 4K and play at 1080p).

No manual sample calibration is required. The detector learns each slot's ready hue and color from saturated corner patches, without matching ability artwork or assuming a particular element. Start detection requires a ready slot and a broad bright neutral use flash; a background edge underneath a charged slot or a moving line inside it cannot start another timer. The original border-only cue was insufficient on translucent, slanted HUD slots. Select and resume detection while abilities are charged; changing the equipped ability/element requires resetting detection to learn its new color.

During charging, a brighter-below boundary supported across both side strips supplies progress, including the HUD's slight upward slant. Boundary searches follow previous progress and widen during visibility loss using the observed charge rate, rather than jumping to an unrelated stronger scene edge. After at least two progress samples, an early line dropout is treated as lost visibility, not completion. The original start timestamp and elapsed timer are kept while waiting for forward progress to return. Near completion (at least 80% observed), a returning ready color must remain visible for 150 ms, with progress seen within two seconds. Signal disappearance alone is not an endpoint; a hidden endpoint is discarded with a warning instead of substituting an estimated duration.

The overlay also shows **estimated total recharge seconds** and **fit confidence** once at least eight spaced progress samples cover one second and 12% of the charge. A rolling linear fit projects the remaining time at the recently observed rate. Confidence is a heuristic based on fit consistency, observation span, and progress coverage, capped at 95%; it is not a calibrated probability or a precision guarantee. Estimates disappear on signal loss, inconsistent/nonlinear progress, or insufficient data and are rebuilt after recovery. Buffs, energy refunds, and other recharge-rate changes can invalidate predictions. Estimates never count as measured results or trigger automatic ability use.

New selections made from the detected game window follow its position and size automatically. Existing display-relative selections can be reselected to enable this. Temporary contrast loss or a temporarily displaced HUD can recover when the signal returns to its capture region before the endpoint. Arbitrary permanent in-game HUD layout changes still require reselection; the app does not scan the entire screen for a replacement icon.

Capture runs on a below-normal-priority worker, defaults to a 120 Hz target, and can be adjusted from 30 to 240 Hz using **Capture target (Hz)**. The worker rests for at least three times each capture's processing duration, limiting capture duty to 25% rather than issuing catch-up bursts under load. Nearby HUD slots share a capture buffer, but widely separated selections are split to avoid copying a large rectangle between them. Native buffers are reused, unchanged overlay text is not repainted, and UI refresh requests are coalesced. The control window reports the measured rate. Desktop GDI capture can still stall on the compositor/GPU; the target is best-effort, not a guarantee of observing every game-rendered frame. Lower the target if capture affects gameplay.

Click the pause-binding button and press any key or mouse button to configure the global pause/resume shortcut; Ctrl, Alt, Shift, and Windows modifiers are recorded with it. Keyboard keys, mouse buttons, and wheel directions are supported. Pressing the shortcut never blocks that input from reaching Destiny 2.

Each ability's **Shortcut** button records a global region-selection shortcut. **Start / stop shortcut** in the repeatability panel records a separate binding that starts the configured test or stops an active one, without switching away from Destiny 2. These are distinct from **Ability use input**, which is the gameplay input sent between test cycles. Bindings must be different from each other; shortcut actions are disabled while the selector is open. Input hooks run on their own message-pump thread and queue actions onto the UI, so a UI/capture stall does not block Windows input processing.

Click the ability-use binding button and press the desired keyboard key, mouse button, or wheel direction; modifiers are recorded as well. To repeat a recharge measurement, select an ability with a configured HUD region, record its ability-use input, set the cycle count and post-recharge delay, then start the test. Manually use the ability once to begin cycle one. After each confirmed full recharge the overlay records its duration; if more cycles remain, it waits the configured delay and sends the recorded input through Windows `SendInput` only when `destiny2.exe` is in the foreground and the selected HUD region still appears charged. If a menu hides the HUD, the next use waits until gameplay is visible again. The test stops after the requested number of measured recharges, reports their average, and can be stopped early with the Stop test or pause control. Settings are stored locally under `%AppData%\D2AbilityTracker`.

## Development and automatic releases

Install the .NET 9 SDK on Windows and run `dotnet run` from this folder to build from source. Run `dotnet run --project tests\D2AbilityTracker.Tests.csproj --configuration Release` for automated checks.

Append `-- --capture-benchmark` to that command for a two-second local GDI capture-rate and capture-duty measurement. This uses a HUD-sized desktop region, not live-game performance validation.

The reference-video regression can be run with `dotnet run --project tests\D2AbilityTracker.Tests.csproj --configuration Release -- --replay "<video.mp4>" "<output.csv>"` with FFmpeg on PATH. It expects the supplied 581x182, 60 FPS, 9,982-frame cropped recording, ignores the pink bar, and processes every frame. It asserts one grenade completion (160.58 s), two melee completions (50.13 s and 50.30 s), one class completion (92.20 s), and an unfinished second class cycle. These are footage-derived observations, not hardcoded gameplay cooldowns; other recordings need their own region and event annotations. Replay success does not guarantee live capture will see every short flash.

GitHub Actions checks formatting, runs the automated checks, and packages a framework-dependent Windows x64 app using Inno Setup. The small installer downloads .NET only if the shared Desktop Runtime is missing; .NET itself is not bundled. CI verifies the Microsoft runtime against its release-metadata SHA-512 hash and embeds its URL and SHA-256 digest for install-time verification. Failed or declined runtime installation blocks setup with an explicit error. Uninstalling the tracker leaves the shared runtime and user settings intact.

Releases use semantic version tags such as `v0.1.0`; installer filenames include that same version, such as `D2AbilityTracker-v0.1.0-Setup.exe`, and the executable's version metadata matches. Each successful `main` update automatically increments the patch version beyond existing releases in the current major/minor series. Set `VersionPrefix` in `D2AbilityTracker.csproj` to start a new minor or major series when changes warrant it; the initial series is `0.1.0` while live-game behavior is still being refined. Release runs on the same branch are serialized to avoid version collisions. Older bundled-runtime releases remain available.

Pull requests produce downloadable workflow artifacts but never releases. You can also run **Build and release** manually from the Actions tab; only runs on `main` publish a release. Repository Actions must be enabled.
